### 2. [설계] 트렌드 데이터 아카이빙 구조 (Data Schema Proposal)

수집된 데이터를 단순히 나열하지 않고, **'검색 가능하고(Searchable)'**, **'관계 중심적이며(Relational)'**, **'확장 가능한(Scalable)'** 구조로 설계해야 합니다.

#### A. 데이터 계층 구조 (Hierarchy)
1.  **Level 1: Era/Period (시대적 배경)** - 예: `2026_Q2`
    *   데이터의 유효 기간을 관리합니다. (과거 데이터 아카이브용)
2.  **Level 2: Category (대분류)** - 예: `Gastronomy`, `Real_Estate`, `Wellness`
3.  **Level 3: Theme (중분류/트렌드 명)** - 예: `Modern_Thai_Fine_Dining`
4.  **Level 4: Entry (개별 데이터/콘텐츠)** - 실제 장소, 리뷰, 사진, 팩트 체크 결과 등

#### B. 데이터 속성 정의 (Data Schema/Fields)
각 'Entry'는 다음과 같은 필드를 포함하여 구조화합니다.

*   **`id`**: 고유 식별자 (UUID)
*   **`timestamp`**: 수집/발행 일시
*   **`category_tag`**: 분류 태그 (Multi-select)
*   **`location_geo`**: 위도/경도 (지도 연동용)
*   **`trend_score`**: 트렌드 강도 (1-5점, 콘텐츠 우선순위 결정용)
*   **`target_relevance`**: 타깃 적합도 (40대 후반 은퇴층 관점에서의 가치 점수)
*   **`content_body`**: 텍스트 데이터 (Writer가 활용할 원천 정보)
*   **`source_link`**: 출처 (사실 확인 및 신뢰도 확보용)
*   **`archive_status`**: `active`(활성), `historical`(과거 기록)

### 3. [전략] 데이터 수집 및 업데이트 프로세스 제안 (Workflow)

이 구조를 바탕으로 에이전트들이 협업할 수 있는 루프를 제안합니다.

1.  **[Research Phase]**: Researcher가 매주/매월 방콕의 새로운 트렌드 데이터를 수집하여 위 스키마 형식으로 정리합니다.
2.  **[Writing Phase]**: Writer가 수집된 `content_body`를 바탕으로 타깃 맞춤형 스토리텔링 콘텐츠를 생성합니다.
3.  **[Design/Dev Phase]**: Designer와 Developer는 `archive_status`에 따라 페이지의 'Latest' 섹션과 'Archive' 섹션에 데이터를 자동 배치합니다.
4.  **[Review Phase]**: 정기적으로 `historical`로 전환된 데이터의 유효성을 검토합니다.
